# BT GAMEPAD 蓝牙手柄 · PC 上位机

配套固件：`D:\minzhan\考核项目\BT GAMEPAD设备\BT GAMEPAD设备工程`（STM32F103RCT6 + RDA5876，裸 HCI 主机栈）。
对应考核项：**BT GAMEPAD 设备 第 5 条 —— 在 PC 上写上位机工具对蓝牙设备进行配置，驱动板载 RGB 灯（10 分）**。
顺带把第 3 条（每个按键和摇杆都能用）在工具里也做了实时显示，演示时不用来回切「游戏控制器」面板。

## 功能

| 区域 | 内容 |
|---|---|
| 顶部 | 枚举系统里所有 HID 游戏控制器（蓝牙/USB 都认）、刷新、连接/断开、掉线自动重连 |
| 摇杆 | 左右两个摇杆的实时位置（原始 ADC 值 + 归一化百分比），十字线标出偏离方向 |
| 按键 | 10 个按键的指示灯与按下次数，底部一行显示"当前按下" |
| RGB | R/G/B 三路滑块 + 数字框、8 个预设色、灯效（常亮/呼吸/彩虹/频闪）、一键演示、拖动即下发、立即下发 |
| 链路状态 | 设备一行摘要（名称 · VID:PID · 蓝牙/USB · IN/OUT 长度）、帧数、报告速率、最近一帧时间、已下发帧数、连接时长、原始报文、按键事件、设备路径 |
| 日志 | 带时间戳的通信日志，可暂停滚动、每帧记录、清空、保存；**导出验收报告**（设备信息 + 链路统计 + 按键计数 + 最近日志，一次存成 txt） |

## 编译

需要 Qt 6（实测 6.12.0 mingw_64）+ MinGW 13.1 + CMake。

```bat
:: 命令行
cmake -S . -B build\Release -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_PREFIX_PATH=D:\QT\6.12.0\mingw_64
cmake --build build\Release -j4
```

或者直接双击 `deploy.bat`：配置 Release → 编译 → 把 exe 和 windeployqt 的依赖一起拷进 `dist\`，
整个 `dist` 目录拷到别的电脑也能双击运行（不需要装 Qt）。

## 使用

1. 手柄上电（固件广播名 **MP GAMEPAD**）。第一次用：Windows「设置 → 蓝牙和其他设备 → 添加设备」里配对上。
   已经配对过的话，手柄上电后按任意键会主动回连，等 5~10 秒。
2. 打开 `dist\btgamepad.exe`，点「刷新设备」，下拉框里应出现 `MP GAMEPAD [蓝牙·本板 045E:0202]`。
   枚举阶段不打开设备，所以 IN/OUT 长度是连上之后才显示在日志里的（本板应为 IN=16B / OUT=9B）。
3. 点「连接」。状态变绿、速率稳定在 ~50 帧/秒，说明 HID 输入通道正常。
4. 推摇杆 → 两个圆里的点跟着动，下面显示原始值（中位 32768）；按键 → 对应的灯亮、次数 +1。
5. 拖 RGB 滑块或点预设色 → 板载 RGB 灯立刻变色。灯效下拉框可以选
   **常亮 / 呼吸 / 彩虹 / 频闪** —— 这三种动效都是上位机按 25 帧/秒算好颜色再下发的，
   板子只负责把收到的 R/G/B 写进 PWM，所以固件端不需要为每种灯效加代码。
   点「一键演示」会按 红→绿→蓝→白→熄灭 各 800ms 走一遍，日志同步打「第 n/5 步」。
   **注意：RGB 需要固件支持输出报告（见下面「固件侧改动」），没烧过这版固件的话灯不会动，
   上位机日志里能看到命令已发出，但板子不会应答。**
6. 想验证"掉线自动重连"：把手柄断电再上电。工具先用原来那条设备路径重试（不动枚举），
   连不上的间隔按 2→4→8→15 秒递增；只有路径失效了才枚举一次找新路径。
   全程只开用户选中的这一台设备的句柄，不会反复开关。日志会写「自动重连成功」。
7. 演示完点「导出验收报告…」，会存一份 txt：设备信息、链路统计、按键次数、最近日志都在里面，
   相当于把"上位机确实驱动了板载 RGB"这件事留了证据。

## 性能监测与测试报告

「性能测试」页只采集真实 HID 数据，不内置演示结果。连接手柄后点击「开始 / 重新测试」，测试期间操作摇杆、按键、RGB 和摇杆配置；可断电重连以采集回连统计。点击「结束测试」后数据冻结，再点击「导出测试报告」。底部「导出报告」按钮使用同一导出功能。

默认生成带内联 SVG 速率曲线的 HTML 报告，也可选择 TXT。报告包含测试时长、有效／无效输入帧、当前与平均速率、最近／平均／最大报告间隔、间隔标准差、超过 30 ms 的间隔、超过 500 ms 的断流、实际输出成功数、Feature 读写结果、连接与回连次数。曲线保留最近 120 个一秒采样窗口，HTML 无需联网即可打开。

手柄输入报告没有序号字段，因此不计算物理丢包；间隔异常与断流也不能冒充丢包。Feature 成功仅表示传输完成，Flash 保存结果以配置页的设备状态回读为准。报告不替代实物功能验收。

## 演示步骤（对着考核第 5 条讲）

1. 手柄上电，Windows 显示"已连接"，**先不打开任何工具** —— 说明链路本身是稳定的。
2. 打开 `dist\btgamepad.exe` → 刷新 → 选中 `MP GAMEPAD … 本板 1209:0001`  → 连接。
   日志会打印 `蓝牙链路 1209:0001 IN=16B OUT=9B`（标准 HID 路径，不再被 xinputhid 接管）。
   连上后日志还有 `[写入] 帧=… → 控制通道:OK（输入不受影响）`，表示 RGB 走的是控制通道，
   彩虹动画不会掐断摇杆/按键。
3. 推摇杆 / 按按键 —— 界面实时跟着动（顺带覆盖第 3 条）。
4. 拖 R/G/B 三个滑块，或点下方预设色块 —— 板载 RGB 立刻变色；
   再把灯效切到「呼吸」「彩虹」各看两秒，说明"颜色和动效都是上位机在配置"。
5. 点「一键演示」，让板子按 红→绿→蓝→白→熄灭 自动走一遍，日志里有 5 行「第 n/5 步」。
6. 说明下行链路：命令是标准的 HID **Output Report（3 号，PID Set Effect）**，
   走蓝牙 HID 控制通道 `SET_REPORT`，固件解析后写 TIM2 的 PWM。
   日志里"已下发：N 帧 RGB"就是上位机实际写出去的帧数。
7. 点「导出验收报告…」存一份 txt 交上去。

> RGB 依赖固件里的 `bt_app_on_output_report()` 以及 `bt_l2cap.c` 中
> `hidp_control_rsp()` 的 `txn=5 / param=2` 控制通道分支。板子里如果还是旧固件，
> 控制通道那帧会被当成 SET_PROTOCOL 丢掉，灯不会亮 —— 这时把
> `Objects\Project.hex`（控制通道 RGB 版）烧一次即可。VID/PID 仍是 1209:0001，
> 不用重新配对，烧完重连即可。

## 为什么"没装上位机时蓝牙很稳，一跑上位机就掉线"

原因不在固件，也不需要重新烧录：旧版上位机的自动重连每 2 秒枚举一次 HID 设备，
而枚举的实现是**对系统里每一个 HID 集合 `CreateFile` 打开、读完属性立刻关闭**。
对 USB 设备这无所谓，对蓝牙 HID 却是致命的 —— 句柄一开，Windows 的 hidbth 就把这条
蓝牙链路建起来；句柄一关，链路被放开。每 2 秒拽一遍，看到的就是"连上一会又掉线"。

现在的做法是把"找设备"和"用设备"彻底分开：

| 动作 | 用什么 API | 会不会碰蓝牙链路 |
|---|---|---|
| 枚举、刷新设备列表 | `GetRawInputDeviceList`（拿 Usage/VID/PID/路径）+ `SetupDi*`（读注册表里的名字） | 不会，全程零句柄 |
| 读摇杆按键、下发 RGB | 只对用户选中的那一台 `CreateFile` 一次，句柄常驻直到断开 | 只影响这一台，且不会反复开关 |
| 掉线自动重连 | **先只对缓存的那一条路径重试 `open`**；打不开才枚举，且枚举最多 15 秒一次；失败间隔 2→4→8→15 秒退避 | 重试只影响这一台，不扫全部设备 |

断线瞬间会先把"刚才连的是谁"存下来（`m_lastDev`），之后的重连完全不依赖
`m_devices` 那份列表 —— 它只是上一次枚举的快照，可能已经过期。
如果手柄断电重连后 Windows 给同一条蓝牙链路分了新的实例路径，缓存路径会打不开，
这时才枚举一次找出新路径；两个路径都试不到就按退避继续等，日志里不会刷屏
（失败重试用的是静默 `open`）。

Raw Input 万一没列出某个集合（极少数驱动不注册），还会用注册表里的接口列表兜底，
保证板子一定出现在下拉框里；它到底是什么用法，等打开时再确认并写进日志。

## 协议

与固件 `hardware/bt_sdp_record.h` 里的报告描述符一致（Usage Page 0x0001 / Usage 0x0005）。

**输入报告 Report ID 1，数据 15 字节**（Windows 读到 16 字节，首字节是 Report ID）

| 偏移 | 内容 |
|---|---|
| 0-1 | X，左摇杆横向，0~65535，中位 32768 |
| 2-3 | Y，左摇杆纵向 |
| 4-5 | Z，右摇杆横向 |
| 6-7 | Rz，右摇杆纵向 |
| 8-9 | LT，10 位 + 6 位填充（本板无模拟扳机，恒 0） |
| 10-11 | RT，同上 |
| 12 | Hat，4 位 + 4 位填充（本板不用，恒 0） |
| 13-14 | 按键 10 位，bit0 = 按键 1 … bit9 = 按键 10 |

**输出报告 Report ID 3，数据 8 字节**（Windows 下发 9 字节）

| 偏移 | 内容 |
|---|---|
| 0 | 命令标记，固定 `0x01` |
| 1 | R，0~100 |
| 2 | G，0~100 |
| 3 | B，0~100 |
| 4-7 | 未用，填 0 |

### 为什么用 3 号报告，而不是新加一个厂商自定义报告

描述符里 3 号本来就是 **PID Set Effect Report**（手柄震动用的输出报告，8 字节）。
直接复用它有三个好处：

- 不用动报告描述符。那份描述符是逐字节手写、已经验证过能配对能开 HID 通道的版本，
  往里插字节要同时改三层长度域（306 / 513 / 642）和内层 SEQUENCE 头，改错就直接连不上；
- Windows 下发输出报告只按声明长度校验（9 字节），不管字段语义，够用；
- 标记字节 `0x01` 放在 Start Delay 字段里（描述符声明是 0~1 的逻辑范围），
  用来把上位机下发的配色和游戏自己发的震动报告区分开。

固件收到后按 `p[0]==0x03 && p[1]==0x01` 判定，取 `p[2..4]` 调 `Tim2_SetRed/Green/BlueBrightness()`。

### 下行链路：上位机只走控制通道

蓝牙 HID 的输出报告可能从两个地方来，固件两条都接了：

1. **HID Control 通道**的 `SET_REPORT`（0x52，参数 0x02 = 输出报告）—— **上位机走这条**；
2. **HID Interrupt 通道**的 `0xA2` DATA 包（固件兼容保留，正常演示不发这条）。

两条路径的数据格式相同（`[Report ID][报告数据…]`），最终都进
`bt_app_on_output_report()`。

> **为什么不能用中断通道下发**：实测（`_rgbdiag/rainbowtest*.c`、`ratetest.c`、
> `cleantest.c`、`coldtest.c`）在 1209:0001 标准 HID 路径上，
> 只要向 Interrupt 通道 `WriteFile` 一次，Windows hidbth 就会把同一条
> L2CAP 中断通道的输入报告挂起约 900ms；彩虹动画 60ms 一帧等于持续掐断
> 摇杆/按键，界面心跳还会误报"链路超时"。哪怕降到 1~2 秒一帧也一样卡。
> 控制通道是独立 L2CAP 通道，实测连续 15 秒、202 帧 RGB 下发，
> 输入始终 50Hz（49~54 帧/秒）、零卡顿。
>
> 固件侧因此补了 `bt_l2cap.c` 里 `hidp_control_rsp()` 的 `txn=5 / param=2`
> 分支：以前 0x52 被当成 SET_PROTOCOL 只回 HANDSHAKE、RGB 全丢，
> 才逼得上位机改走中断通道。现在控制通道能真正点亮 RGB。
> **演示前必须烧录这一版固件**（`Objects/Project.hex`），否则灯不会亮。

## 固件侧改动（本次一并完成）

> 蓝牙栈本身用的是备份工程 `_backup_bt_gamepad_20261116_213104`（11/16 21:31）里那版，
> 逐行对齐，只补了考核必需的三处：设备名 `MP GAMEPAD`（第 1 条）、
> 按键唤醒回连（第 4 条）、输出报告驱动 RGB（第 5 条）。
> 换回后 `bt_evt.c` / `bt_hci.c` / `Init_rda5876.c` 与备份**完全相同**，
> 所以串口日志会比之前啰嗦（备份版默认开着 HCI 抓包 `BT_HCI_TRACE 1`）。

| 文件 | 改动 |
|---|---|
| `hardware/bt_gamepad.c` | 新增 `bt_app_on_output_report()`：解析 3 号报告、限幅到 0~100、调 TIM2 PWM；值不变不重复写寄存器 |
| `hardware/bt_l2cap.c` | HID Interrupt 通道加 `0xA2` 分发；`SET_REPORT`（输出报告）不再丢弃，转给上面那个函数 |
| `hardware/bt_hci.h` | 导出 `bt_app_on_output_report()` 声明 |
| `User/main.c` | 调 `Tim2_Init()` 把 PC7/PC8/PC9 配成 1kHz 软件 PWM，初始全灭 |

上电时灯是全灭的 —— 演示时"电脑点一下颜色，板子才亮"，能直接证明蓝牙 HID 下行是通的，
而不是上电自带的灯效。

## 排查

| 现象 | 检查 |
|---|---|
| 下拉框里没有设备 | 手柄是否已配对/回连成功；「设备管理器 → 人体学输入设备」里有没有 HID 游戏控制器；点「刷新设备」 |
| 有设备但连不上 | 关掉「游戏控制器」属性面板和正在读手柄的游戏（它们可能独占设备），再点连接 |
| 连上但收不到报告（速率 0） | 看固件串口日志 `[bt] state=3` 和 `reports=` 是否在增长；HID Interrupt 通道没开时固件不发帧 |
| 灯不跟着变色 | 固件串口应有 `[rgb] R=.. G=.. B=..`；没有说明输出报告没到，检查 `SET_REPORT` 分支和 3 号报告长度 |
| 日志一片空白 | 勾上「记录每一帧」；或点「刷新设备」看扫描结果 |

## 代码结构

```
main.cpp        入口：Fusion 风格 + 字体 + 窗口
mainwindow.h/.cpp  界面：StickPad（自绘摇杆）、KeyIndicator（按键灯）、ColorSwatch（色块）+ 主窗口
hiddevice.h/.cpp   Windows HID 层：SetupAPI 枚举、重叠 I/O 读写线程、失败限流
protocol.h         报告格式、解析、组帧（与固件一一对应）
```

界面线程不碰任何 HID 传输：

- 读线程拿到报告 → 信号发到界面 → 只存"最新一帧 + 脏标志"；
- 摇杆/按键的实际重绘由 50ms 的定时器统一做（20Hz），蓝牙 50Hz 的报告不会变成 50 次/秒重绘；
- RGB 下发由 40ms 单次定时器合并（最多 25 帧/秒），队列里连续的配色帧只保留最后一帧；
- 写线程里 `WriteFile` 超时 250ms 就 `CancelIoEx`，绝不把界面拖住。
